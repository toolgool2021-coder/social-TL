# NEXORA 3.2 — Firebase: состояние и выпуск

Дата: 14 ноября 2026. Это первый этап интеграции; [полный объём требований](NEXORA_3_2_ROADMAP.md) остаётся в работе.

## Проверка и изменения

- 31 тест безопасности Firestore Emulator и 10 дополнительных сравнительных тестов старых/новых правил: регистрация профиля, старые профили, публикации/комментарии/подписки/сохранение, чаты двух пользователей, стикер-сообщения, реакции, редактирование, прочтение; запреты анонимного и постороннего доступа, эскалации ролей и подделки времени.
- Изолированные проверки реального клиентского кода с имитацией DOM/Firestore: гонка регистрации, восстановление частичного аккаунта, сохранение legacy-привилегий, realtime комментарии, черновики, переключение A → B → A, мобильная кнопка «Назад», фоновая вкладка и выход.
- Проверки шести реальных обработчиков Cloud Functions с имитацией транспорта: адресаты, retry, сохранение read, новые повторные подписки/лайки, коллизии ID, ошибки и некорректные старые данные. Firebase SDK отдельно загружается с установленными зависимостями.
- Выгрузка правил проверена с имитацией API: активный release, контроль проекта/содержимого, SHA-256, защита от перезаписи и ошибки доступа.

**Рабочий Firebase не изменён.** Эмулятор и VM-тесты не подтверждают опубликованный сайт, настройки Authentication, доставку email, регион базы или IAM. Браузерная проверка с двумя настоящими аккаунтами в staging ещё требуется.

Исправлены согласованное создание профиля транзакцией, realtime-комментарии с сохранением формы при обновлении ленты, lifecycle чатов/черновиков/прочтения, истечение typing/presence и атомарные реакции. Уведомления используют ID CloudEvent: retry не создаёт копию и не сбрасывает read, новое реальное событие создаёт новое уведомление.

Правила проверяют новые URL и временные метки, запрещают комментарии к отсутствующим постам и изменение реакций удалённых сообщений. Старые профили без createdAt и с некорректными неизменяемыми полями остаются редактируемыми; пустые URL допустимы. Поддерживается старое readAt: null. Миграция данных не выполняется.

## Форматы данных

| Путь | Формат / доступ |
| --- | --- |
| users/{uid} | name, bio, опционально username/avatarUrl/bannerUrl/websiteUrl/pinnedPostId; role и verification изменяет фиксированный владелец |
| posts/{id} | uid, text, опционально imageUrl, createdAt |
| posts/{id}/comments/{id} | uid, text, createdAt; новый комментарий требует существующий пост |
| users/{uid}/likes/{postId}, saved/{postId} | Только createdAt; приватные записи владельца аккаунта |
| users/{uid}/followers/{uid}, following/{uid} | createdAt; клиент пишет обе стороны подписки транзакцией |
| users/{uid}/notifications/{id} | Сервер: text/kind/targetId/actorId/read/createdAt; пользователь отмечает свои прочитанными |
| chats/{id} | Два участника; новые ID — отсортированные UID через _; updatedAt, lastText, опционально закрепление |
| chats/{id}/messages/{id} | senderId/type/text/sticker/createdAt, опционально replyTo/replyText/editedAt/readAt |
| chats/{id}/reactions/{messageId}_{uid} | uid/messageId/emoji/createdAt; одна реакция пользователя |
| chats/{id}/typing/{uid}, presence/{uid} | Собственная запись с серверным временем |
| verificationRequests/{uid}, reports/{id}, auditLogs/{id} | Заявки/жалобы; решения и журнал ограничены владельцем |

Новые даты записи — serverTimestamp(). Старые даты не переписываются. Владелец требует существующий UID FXtmMsn8JYfx04zpxiSaXZ0iHWg2 **и** server-assigned role=owner. Клиент не может назначить эту роль себе.

Старые чаты с неканоническими ID доступны участникам, но автоматического переноса нет. Старые messages.reactions не удаляются; новый клиент показывает отдельную коллекцию реакций. Импорт старых карт требует отдельной проверки.

firestore.indexes.json — пустая исходная конфигурация, не backup production-индексов. Текущие запросы используют одиночные индексы. **Не разворачивать пустой файл поверх рабочих индексов.**

## Локальные проверки

Node.js 22, Java 21:

```bash
npm ci
npm ci --prefix functions
npm test
```

Отдельно: npm run check, npm run test:unit, npm run test:rules. Эмулятор использует только demo-nexora-rules-test, не рабочий toolchat-bfac8. Если домашний каталог недоступен для записи, задайте npm_config_cache, FIREBASE_EMULATORS_PATH и XDG_CONFIG_HOME путями внутри /tmp.

CI устанавливает два lock-файла и запускает проверки кода, unit-тесты и эмулятор. Наличие workflow не означает успешный запуск GitHub Actions.

## До рабочего обновления

1. Подтвердить **активные** правила. Полный исходник 3.0, присланный пользователем, теперь сохранён без изменений с SHA-256 и [подробно сопоставлен с кандидатом](docs/firebase/COMPARISON_3_0_TO_3_2.md). Все прежние разделы сохранены, изменения поведения проверяются на обеих версиях в эмуляторе. Публикация этого исходника в действующем Firebase независимо не подтверждена: перед выпуском нужен свежий экспорт или подтверждение соответствия активной версии. Инструмент только читает API:

   ```bash
   # FIREBASE_ACCESS_TOKEN задаётся локально из авторизованной Google-сессии.
   # Не вставлять токен в чат или коммит.
   npm run backup:rules -- --project toolchat-bfac8
   ```

   Требуется OAuth access token с правом чтения Firebase Rules API. Результат: deployment-backups/<project>-<UTC date>/ с firestore.rules, manifest.json, release/ruleset и SHA-256; каталог исключён из Git. Если API недоступен, экспортировать через Firebase Console и отдельно сохранить проект, дату, ruleset ID и контрольную сумму.
2. Сравнить экспорт с кандидатом: diff -u <backup>/firestore.rules firestore.rules. Проверить фактические коллекции/legacy-форматы. Сохранить отдельно рабочие индексы, список функций и настройки. Backup правил не заменяет backup данных; этот этап данные не мигрирует.
3. Настроить отдельный staging Firebase: Authentication, разрешённый домен/redirect email, регион Firestore и права. Сейчас клиенты указывают на production: **он не является staging**. Заменить конфигурацию Firebase во всех клиентах staging-копии. Триггеры сейчас в us-central1; согласовать регион с базой до выпуска.
4. Применить кандидат только в staging. Functions разворачиваются отдельно после проверки тарифа, стоимости и разрешения владельца. Не включать billing автоматически. Проверить существующие функции, не удалять их общей командой deploy.
5. Пройти сценарии ниже. Только после успешной приёмки согласовать рабочее обновление.

## Браузерная приёмка двумя аккаунтами

| Сценарий | Ожидаемый результат |
| --- | --- |
| Регистрация A/B, выход/вход, email | Один профиль, правильное имя, рабочая ссылка email, интерфейс загружается |
| Старый профиль и пустые URL | Сохраняются изменения, пользователь не меняет свою роль/значок |
| Пост A, лайк/комментарий B, сохранение | Обновления без reload, открытый комментарий сохраняет ввод |
| Подписка/отписка/повторная подписка | Обе стороны согласованы, новые события дают уведомления |
| Новый чат A↔B, ответы/реакции/редактирование/удаление/закрепление | Нет permission-denied, чужое сообщение нельзя изменять |
| A → B → A и мобильная кнопка «Назад» во время отправки | Черновики не затираются, скрытый чат не отмечается прочитанным |
| Фоновая вкладка B, сообщение A, возврат B | Прочтение только после возврата к активному диалогу |
| Уведомления и повтор CloudEvent | Одна запись на событие, read сохраняется, новые реальные события не теряются |
| Жалоба/заявка, решение владельца, журнал | Обычный пользователь не выдаёт себе роль, значок или решение |
| Экран 360px, клавиатура, reduced motion | Доступны навигация/композер, нет перекрытий |

В репозитории нет рабочего стикерпака по требуемому пути image/stic/<pack>/. Пустой image/sticker/Pack_1/Test не является стикером; приёмка настоящих стикеров и управления паками требует реализации и ресурсов.

## Выпуск и откат

Зафиксировать SHA кода, backup правил, список функций, проект и результаты staging. Клиент и правила публикуются согласованно: старые правила могут запрещать новую коллекцию реакций. Проверить после выпуска ленту, новый чат и уведомления. При отказах вернуть сохранённые правила и предыдущую клиентскую версию; отдельно вернуть версии изменённых функций. Индексы и миграции данных не включать в такой откат.

Этот этап не завершает Assistant, серверный антиспам, уникальность username, фактическую приватность/блокировки, Storage Rules/загрузку медиа, реальные стикерпаки, опросы/рекомендации, команды модерации и редизайн. См. полную дорожную карту.
